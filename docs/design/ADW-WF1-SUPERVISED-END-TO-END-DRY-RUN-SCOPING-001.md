# Workflow v1 supervised end-to-end dry-run scoping

## Decision

`authorize-one-supervised-end-to-end-workflow-dry-run`

Authorize one bounded, serialized and supervised dry run of the accepted Workflow v1 semantic and tooling-design basis. The dry run will produce one useful repository navigation improvement and exercise the protected publication lifecycle from exact task authority through candidate production, producer verification, fresh independent review, coordinator acceptance and exact protected publication.

This decision is not Workflow v1 adoption. It creates no routine, parallel, automated, unattended or AFK authority and resolves no RG gap. It authorizes only the bounded candidate contract below, followed by its separate review, acceptance and publication gates.

## Selected useful outcome

The dry run will add one concise `Protected supervised publication` section to `README.md`.

The section must:

1. explain that separately authorized supervised repository writes use a bounded candidate branch, draft pull request, exact-candidate independent review, coordinator acceptance and separately authorized merge;
2. link to the protected-path operational-use decision and to the Research Register;
3. state that the Register remains the sole owner of the mutable current gate;
4. state that using the publication mechanism does not authorize a substantive change;
5. state that direct-main, parallel, automated, unattended and AFK writes remain unauthorized and that Workflow v1 remains unadopted;
6. remain stable navigation rather than duplicate the current gate, live SHA, ruleset configuration or changing project status.

The README is navigation only. It does not become a policy, task tracker, mutable gate owner or acceptance record.

## One candidate contract

The dry-run candidate may change exactly:

- add `docs/design/ADW-WF1-SUPERVISED-END-TO-END-DRY-RUN-SCOPING-001.md` byte-for-byte from this coordinator record;
- modify `README.md` only for the selected navigation section;
- modify `docs/research/research-register.md` only for the minimal dry-run decision pointer and post-publication next-gate transition.

No separate repository artifact is required solely to authorize mechanical gate persistence. The scoping decision and selected README outcome may be carried by the same immutable candidate because this exact contract already authorizes both, and protected publication prevents either from reaching `main` before fresh review and coordinator acceptance.

Default candidate shape:

- exact base: current live `main` at dispatch;
- one task-owned branch: `adw/wf1-supervised-e2e-dry-run-001`;
- one candidate commit unless a pre-mutation blocker stops execution;
- one authenticated non-force branch push, no silent retry;
- one draft PR with `maintainer_can_modify=false`, no auto-merge and no requested reviewers;
- `main` unchanged until later exact acceptance and merge authority.

## State and role ownership

- Command Center owns task authority, this scoping decision, coordinator acceptance and the next-gate decision.
- The Research Register remains the sole repository owner of the mutable current gate.
- One Codex executor owns candidate production and producer verification for the bounded task only.
- One fresh Independent Review context owns review findings and recommendation for the exact immutable candidate only.
- The user remains supervisor and external-mutation authority.
- GitHub owns branch, PR, commit, merge and ruleset observations; those product states do not replace Workflow v1 state planes.

No chat, runner, branch or PR independently owns the current gate.

## Lifecycle exercised

The episode must preserve this sequence:

1. authoritative reread and exact-base task authorization;
2. readiness and applicability evaluation;
3. serialized candidate production on one bounded branch;
4. producer verification of complete delta, bytes, identities, constraints and prohibited effects;
5. one draft PR with `main` unchanged;
6. fresh independent review bound to the exact terminal candidate SHA;
7. correction by a new candidate identity if a material finding exists;
8. coordinator acceptance bound to the exact reviewed candidate;
9. separately authorized ready transition and merge with exact expected head;
10. publication readback of commit, ordered parents, tree, complete delta, Register and ruleset;
11. return to Command Center for adoption-readiness assessment.

Review evidence is not inserted into an already reviewed candidate. A local review record may remain external evidence. This avoids recursive review while preserving exact review binding.

## Producer-verification minimum

Before branch publication, the executor must report and retain enough evidence to establish:

- exact base commit/tree and input blobs;
- clean isolated worktree and one-writer declaration;
- exact authorized path set;
- byte equality for this scoping record;
- README section constraints and link validity by inspection;
- exact Register reconstruction and occurrence checks;
- encoding, line endings, final newline and modes for changed files;
- `git diff --check` and complete staged delta;
- candidate commit, tree, sole parent and message;
- branch push attempt count and result;
- draft PR base/head/state and unchanged live `main`/ruleset;
- explicit absence of unapproved effects.

The evidence may be reported from the task and reconstructed from GitHub. No standalone evidence package, schema, checker invocation or new repository evidence file is required for this low-risk documentation dry run.

## Acceptance criteria

The dry run succeeds only if:

- the selected README section is accurate, concise, useful and non-authoritative;
- the candidate and publication contain exactly the authorized paths and semantics;
- all state planes and owners remain distinct;
- producer verification is complete and independently inspectable;
- fresh independent review has no unresolved BLOCKER, MAJOR or MINOR finding;
- coordinator acceptance binds the exact reviewed candidate;
- protected merge binds the exact accepted head and yields the expected tree/content;
- final readback proves the Register transition and unchanged ruleset;
- no retry, correction or failure history is hidden;
- no denied execution mode is exercised or implied.

Successful publication is evidence for the later adoption-readiness assessment. It does not itself adopt Workflow v1 or prove every semantic path, failure mode or RG control.

## Denied scope

This gate does not authorize:

- direct-main writes or ruleset bypass;
- parallel writers or multiple candidate branches;
- automated, unattended or AFK execution;
- Actions, hooks, required checks, bots, orchestration or new tooling;
- persistence-checker execution;
- product-project dogfooding;
- a task schema, tracker, Issue workflow or duplicate current-state owner;
- branch cleanup;
- changes to Charter, AGENTS.md, policies, accepted designs or ruleset;
- Workflow v1 normative adoption;
- declaration that RG1 through RG12 are resolved.

DI-1 and DI-2 remain preserved. Any material drift, conflicting authority, unexpected path, stale subject, ambiguous mutation result or unavailable required evidence fails closed.
